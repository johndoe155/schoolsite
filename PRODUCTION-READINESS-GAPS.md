Also fixed in this pass (found while building the above, each one a real defect):

- **A server-rejected offline register looked exactly like a pending one.** `POST /sections/:id/attendance` is replay-safe and the queue retried correctly, but the banner on screen said "waiting for a connection" for every failure — 409 (finalized elsewhere), 422 (pupil no longer enrolled) and 403 (session ended) all looked the same, so nobody would ever act on it. Rejections are now listed by date with the server's own reason, and the queue keeps the marks until a human deals with them.
- **Classwork ownership was enforced only by RLS.** Asking for another family's child returned `200 []` — indistinguishable from a child with no homework, and invisible if a policy broke. Now `403 not_your_record`.
- **`bootstrap-live.mjs` shipped a published bootstrap password** (`Passw0rd!Policy1`) and renamed the school to "Bright Future Academy". It now refuses to run without an explicit `LIVE_PROOF=1`, a caller-supplied admin password, and a fresh database.
- **Portal uploads had no volume** in `docker-compose.yml`, so every worksheet vanished on redeploy while its database row survived (a download link that 404s). `portal_files` volume added, and the backup sidecar now archives it.
- **`restore.sh` could restore the database but not the site content** the backup script had been collecting. `--site [--latest] [--list]` added and drill-tested; the flag-order bug (`--site --latest` picking a database dump) was found and fixed by its own dry run.
- **Root `npm audit` failed CI on an advisory with no patched release** (braces/micromatch via Tailwind and the proxy). Replaced with `scripts/audit-gate.mjs`: failures for advisories fixable in place, loud amber notices for the ones that need a semver-major elsewhere. `nodemailer` bumped to v10.
- **A root `loading.tsx` turned every `redirect()` into a streamed 200** (Next 16 streams from the moment the loading boundary appears). Removed; the anon redirect is a 307 again.
- Test hygiene: the classwork suite had a fixture that made an old assertion pass for the wrong reason (one row per enrolled pupil), and the smoke suite's preference check counted categories instead of naming them (phase 8 added a fifth).

Test state after this pass: API **298/298**, web smoke **91/91** through `:4040` (the origin a browser actually uses), site route + proxy matrix green, portal audit 0.

## 1. Your three findings — checked and expanded

### 1.1 Timetable — you are right about the UI, but there is a backend ✅→❌
The last commit (`ae1fbb3`) added a real timetable: `timetable_periods` / `timetable_slots` (migration `0018`), clash detection, break handling, audit, and 10 passing tests (`portal/apps/api/test/timetable.test.mjs`).

What is missing:
- **No UI anywhere.** `grep -rn "timetable" portal/apps/web` returns only two comments in the rollover panel. There is no admin builder for the bell schedule or slots, no teacher "my week" view, no student/parent view.
- **Students and parents cannot read it even via the API.** `student: ["self:read"]` and `parent: ["family:read","fees:pay"]` in `portal/apps/api/src/seed.ts` have no `schedule:read`; the only read endpoints (`GET /timetable/me`, `GET /timetable/sections/:id`) are gated on it.
- `GET /timetable/me` is written as "a teacher's week" (it filters `timetable_slots.teacher_user_id = caller`), so it is the wrong shape for a pupil.
- No student/parent endpoint exists (`/student/timetable`, `/parent/children/:id/timetable` — absent).

**Consequence for day one:** the school will run the timetable on paper/Excel while the portal claims to have one; the "clash detection" nobody can see prevents nothing.
**Effort:** ~3–5 days (admin builder 1.5 d, teacher view 0.5 d, student + parent endpoint + view 1 d, permissions/migration + tests 1 d).

### 1.2 Homework / assignments / file sharing — confirmed absent ❌
No assignment entity exists. `grades.source_type` has a CHECK allowing `'assignment'`, but there is no assignment table, no due date, no submission, no attachment, no material/resource library. Messaging (`message_threads`, `messages`) has **no attachments** (no upload path, no storage, no MIME allowlist in the message body schema) and no read receipts.

This spans three separate product asks, and they should be scoped separately:
- **Homework/assignments** — assignment + due date + per-student submission state; needs a decision on whether students upload files or just mark "done".
- **Class materials / file sharing** — teacher uploads a PDF to a section; needs the storage story in 1.4.
- **Report card / fee PDFs** — also missing (see P1-2).

**Roadmap status:** `portal/docs/production-roadmap.md` lists *"File storage (materials/uploads): S3-compatible bucket, presigned URLs, MIME allowlist, per-object RLS"* as 📋 backlog — i.e. this is the known gap behind all of the above.
**Effort:** assignments ~1 week; materials/file sharing ~1 week on top of storage (see P1-6).

### 1.3 Mobile / PWA / offline — confirmed absent ❌
- **No service worker, no web app manifest, no offline queue anywhere** — the only hits for "serviceworker/manifest/workbox" in the repo are in a CI file and a design doc.
- The teacher attendance register (`/teacher/attendance/[sectionId]`) and gradebook are ordinary server-rendered web forms: they need a live connection on every keystroke/save. In a Nigerian school the realistic rhythm is "teacher marks the register on a phone in a classroom with poor data" — a dropped request currently loses the register.
- **The portal's own roadmap lists this as backlog:** *"PWA / offline attendance: service worker + IndexedDB queue for teacher registers."*
- There is no `viewport`/safe-area or install-prompt work, and one portal CSS file has only 3 `@media` rules (two are `min-width: 768px`) — it is responsive-ish, not mobile-first, and has never been tested on a low-end Android.

**Effort:** ~1–1.5 weeks (manifest + SW + offline attendance queue + sync/conflict rules + idempotency proof). Idempotency infrastructure already exists (`idempotency_keys`), which makes the sync side much cheaper than it sounds.

## 4. P2 — first month (real value, not launch-critical)

- **P2-1 Backup depth:** nightly dumps give **RPO ≤ 24 h** (documented in `docs/backup-restore.md`); no PITR unless the managed Postgres provides it. Decide whether 24 h of lost marks/payments is acceptable, and if not, turn on PITR.
- **P2-2 Offsite backup target:** `BACKUP_S3_BUCKET` is optional; with it empty, `/health` warns *"backups are not being copied off this host"* and a host failure loses everything (including the only copy of the site's content tarball).
- **P2-3 Container resource limits & restart tuning:** no `deploy.resources`/memory caps on `postgres`, `api`, `worker`, `web`, `site` — one leaky process can OOM the school's whole website.
- **P2-4 Security review & hardening of the host:** firewall, SSH key-only, fail2ban, unattended upgrades, Docker socket hygiene (`ufw`/`fail2ban`/`unattended-upgrades` appear nowhere in the docs), plus an OWASP ZAP baseline and an external pentest (promised in the architecture doc, never run).
- **P2-5 Compliance paperwork:** Nigeria Data Protection Act/NDPC posture — controller registration where applicable, DPIA, records of processing, data-processing agreements with the host/SMTP/Paystack providers, a named DPO with a published address, plus the offline consent forms for guardians (the portal currently holds **no date of birth and no guardian-consent record**, so it cannot identify under-13s; the legal pages now say so plainly rather than claiming a COPPA gate that does not exist).
- **P2-6 Staff training & documentation:** there is no end-user guide for the marketing site (how to add a news post, upload gallery images, publish a library PDF, change the homepage hero) or for the portal (attendance, gradebook, fees, imports) — the docs are engineering/ops-facing (`pilot-runbook.md` is the closest). Teachers need a 1-page cheat sheet, and the office needs a named first-line support person.
- **P2-7 SMS/WhatsApp + push channel** (see P1-3) and **WebSockets/live updates** (currently polling + digest, roadmap backlog).
- **P2-8 Test depth:** no Playwright/browser e2e (backlog), no accessibility suite, no visual regression; k6's full 50-VU/300 req/s profile is manual-only.
- **P2-9 Operations calendar:** restore drill quarterly (weekly for the newest backup is automated — confirm someone *reads* the result), secret rotation schedule, dependency patching cadence, and a documented incident/rollback procedure with the school's escalation contacts.
